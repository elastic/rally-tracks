# API Keys Track

Benchmarks Elasticsearch API key authentication. The track creates a configurable population of native roles, native users
and REST API keys owned by those users, and then measures [`GET /_security/_authenticate`](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-security-authenticate)
authenticated with those API keys.

The track is meant to detect regressions in the API key authentication path and to give insight into what can be optimized
there (for example together with JFR flame graphs via `--telemetry=jfr`).

## What a request exercises

Authenticating a REST API key against `_security/_authenticate` runs through:

1. API key document lookup: the API key *document cache* (`xpack.security.authc.api_key.doc_cache.ttl`, 5 minutes by
   default, bounded by `xpack.security.authc.api_key.cache.max_keys`) or, on a miss, a `GET` of the key document from the
   `.security` index.
2. Credential verification: the API key *authentication cache* (`xpack.security.authc.api_key.cache.ttl`, 24 hours by
   default, `cache.max_keys` entries, 25,000 by default). On a miss the stored hash of the key is verified
   (`xpack.security.authc.api_key.hashing.algorithm`) and the result is cached (`xpack.security.authc.api_key.cache.hash_algo`).
3. Authorization: role descriptors of the API key and of its owner are resolved through the role cache
   (`xpack.security.authz.store.roles.cache.max_size`). Roles are only built on a role cache miss.

The population generated by this track is deterministic for a given `seed`, so races against different Elasticsearch
revisions see exactly the same roles, users, API keys and request sequence.

## Prerequisites

**Security must be enabled** on the target cluster and Rally must connect with a superuser (for Rally-provisioned
clusters use the `x-pack-security` car mixin and the `rally` user, see the examples below).

API keys are written to `api_keys_dir` (`~/.rally/benchmarks/data/api_keys` by default) by the `create-api-keys` task and
read from there by the authentication tasks. Rally runs one worker process per CPU core, so this directory must be
accessible by all Rally worker processes (it is, for a single load driver host).

## Parameters

All parameters can be set via `--track-params`.

### Population

| Parameter | Default | Description |
|-----------|---------|-------------|
| `seed` | `42` | Seed for all generated data. Keep it fixed when comparing Elasticsearch revisions. |
| `num_roles` | `100` | Native roles to create. Each role has 1-3 cluster privileges and 1-3 index privilege entries with wildcard patterns. |
| `num_users` | `100` | Native users to create. Users are the owners of the API keys; the privileges of the owner become the *limited-by* role descriptors of the key. |
| `roles_per_user` | `2` | Roles assigned to each user (must not exceed `num_roles`). |
| `kibana_app_privileges` | `false` | Add a `kibana-.kibana` application privilege to every role. Building such roles requires application privilege lookups in the `.security` index on role cache misses. |
| `num_kibana_spaces` | `100` | Number of Kibana spaces used as application privilege resources (only with `kibana_app_privileges`). |
| `num_api_keys` | `10000` | API keys to create. `10000` fits into the default API key caches (`cache.max_keys: 25000`); `100000` exceeds them 4x and causes continuous cache evictions. |
| `num_rd_templates` | `50` | Number of distinct role descriptor sets assigned to API keys. Keys sharing a template have byte-identical role descriptors and share the role descriptor and role cache entries. |
| `assigned_rd_ratio` | `0.5` | Fraction of API keys with assigned role descriptors. The other keys have empty role descriptors and inherit the privileges of their owner. |
| `api_key_expiration` | unset | Optional expiration of the created API keys, e.g. `30d`. |
| `api_keys_dir` | `~/.rally/benchmarks/data/api_keys` | Directory for the API key files and the server-side stats snapshot. |

### Schedule

| Parameter | Default | Description |
|-----------|---------|-------------|
| `create_clients` | `8` | Clients creating API keys. Each client writes its own `api-keys.<client>.jsonl` shard. |
| `create_batch_size` | `100` | API keys created concurrently per client and iteration. Creation uses the grant API with `refresh=wait_until`, so the creation throughput is roughly `create_clients * create_batch_size` keys per refresh interval. |
| `clients` | `8` | Clients for `prime-api-key-caches` and `authenticate-api-key`. |
| `warmup_time_period` | `60` | Warmup period of `authenticate-api-key` in seconds. |
| `time_period` | `300` | Measurement period of `authenticate-api-key` in seconds. |
| `target_throughput` | unset | Target throughput (requests per second) of `authenticate-api-key`. If unset, clients run unthrottled. |
| `access_pattern` | `uniform` | Key selection of `authenticate-api-key`: `uniform` picks a uniformly random key per request (worst case for the LRU caches when the population exceeds the cache capacity); `hotset` sends `hot_ratio` of the requests to `hot_fraction` of the keys. |
| `hot_fraction` | `0.01` | Fraction of keys in the hot set (`access_pattern: hotset`). |
| `hot_ratio` | `0.9` | Fraction of requests targeting the hot set (`access_pattern: hotset`). |
| `invalid_credentials_ratio` | `0.0` | Fraction of requests using an existing API key id with a wrong secret (expects HTTP 401). Note that Elasticsearch logs a warning for every failed authentication, which adds logging overhead on the server. |
| `cleanup` | `false` | Invalidate all created API keys and delete the users and roles at the end. Useful for persistent clusters. |

## Challenge `api-key-authentication` (default)

| Task | Description |
|------|-------------|
| `create-roles-and-users` | Creates `num_roles` roles and `num_users` users. |
| `create-api-keys` | Creates `num_api_keys` API keys via `POST /_security/api_key/grant` on behalf of their owners and persists them to `api_keys_dir`. Reported in keys per second. |
| `prime-api-key-caches` | Authenticates with every API key exactly once (all clients together). This fills the API key document cache (and the role cache) when the population fits into the caches. Note that creating an API key already populates the authentication cache, so the stored hash is only verified during priming for keys that have been evicted since their creation, i.e. when the population exceeds `cache.max_keys`. |
| `collect-security-stats-before` | Snapshots server-side counters (see below). |
| `authenticate-api-key` | The measured task: `GET /_security/_authenticate` with API keys selected according to `access_pattern`. |
| `collect-security-stats-after` | Snapshots server-side counters again and reports deltas. |
| `cleanup` | Only with `cleanup: true`. |

### Server-side counters

The `collect-security-stats-*` tasks store the following values as request meta-data of their samples in the Rally metrics
store (`rally-metrics-*`, fields `meta.*`) and log them to `rally.log`. The `*-after` task additionally reports `*_delta`
values for the measurement window and the derived `cpu_micros_per_authenticate`, `security_crypto_tasks_per_authenticate`
and `security_index_gets_per_authenticate`.

| Value | Source | Meaning |
|-------|--------|---------|
| `security_crypto_completed` | `GET _nodes/stats/thread_pool` | Hash computations forked to the `security-crypto` thread pool. |
| `security_index_get_total` | `GET .security/_stats/get` | Document fetches from the `.security` index, i.e. API key document cache misses (plus a few user lookups). |
| `authenticate_requests` | `GET _nodes/stats/http` (`http.routes`) | HTTP requests on `/_security/_authenticate`. |
| `process_cpu_millis` | `GET _nodes/stats/process` | CPU time consumed by the Elasticsearch process(es). |

Enable `--telemetry=node-stats` to additionally record these counters as time series.

## Scenarios

The API key caches are configured with static node settings, so the Elasticsearch-side variants need separate clusters
(for Rally-provisioned clusters use `--car-params`, see below), while the population and access pattern are track
parameters. Use a single Elasticsearch node: the caches are per node and the `.security` index is local to the node.

| Scenario | Track parameters | Elasticsearch settings | Measures |
|----------|------------------|------------------------|----------|
| Caches fit | `num_api_keys:10000` | defaults | Steady state with all caches hit: cache hash verification plus role cache lookups. |
| Caches exceeded | `num_api_keys:100000` | defaults | Continuous misses and evictions: `.security` document fetches, stored hash verification, cache hash computation, eviction bookkeeping. |
| Hot set | `num_api_keys:100000,access_pattern:hotset` | defaults | Skewed access with a population exceeding the cache capacity. |
| Caches disabled | `num_api_keys:10000` | `xpack.security.authc.api_key.cache.ttl: 0s` | Every request fetches the key document and verifies the stored hash. Note that this setting disables the document cache as well. |

Measure the fast path in two modes: unthrottled (`target_throughput` unset, 16-32 clients) for maximum throughput and
service time percentiles, and with a fixed `target_throughput` below saturation for latency percentiles and CPU per
authentication (`cpu_micros_per_authenticate`).

## Usage examples

### Rally-provisioned cluster

```bash
esrally race --track-path=api_keys --distribution-version=9.5.4 \
  --car="4gheap,trial-license,x-pack-security" \
  --client-options="use_ssl:true,verify_certs:false,basic_auth_user:'rally',basic_auth_password:'rally-password'" \
  --track-params="num_api_keys:10000,clients:16" \
  --telemetry=node-stats --user-tag="scenario:fit"
```

Caches exceeded, with the API key caches disabled on the Elasticsearch side:

```bash
esrally race --track-path=api_keys --distribution-version=9.5.4 \
  --car="4gheap,trial-license,x-pack-security" \
  --car-params='{"additional_cluster_settings": {"xpack.security.authc.api_key.cache.ttl": "0s"}}' \
  --client-options="use_ssl:true,verify_certs:false,basic_auth_user:'rally',basic_auth_password:'rally-password'" \
  --track-params="num_api_keys:10000,clients:16" \
  --telemetry=node-stats --user-tag="scenario:no-cache"
```

### Existing cluster

```bash
esrally race --track-path=api_keys --pipeline=benchmark-only --target-hosts=localhost:9200 \
  --client-options="use_ssl:true,verify_certs:false,basic_auth_user:'elastic',basic_auth_password:'changeme'" \
  --track-params="num_api_keys:100000,clients:16,cleanup:true"
```

### Comparing Elasticsearch revisions

Run the same track parameters (including `seed`) against both revisions, e.g. with `--pipeline=from-sources --revision=<sha>`,
and compare with `esrally compare`. The server-side counters tell apart changes in the number of hash computations forked
to `security-crypto`, in the number of `.security` document fetches and in CPU per authentication.

## Notes

* `GET /_security/_authenticate` also resolves the roles of the API key; the role cache is warm after `prime-api-key-caches`
  because the number of distinct role descriptor sets (`num_rd_templates` plus one per user) is far below the role cache size.
* The API key document cache expires entries 5 minutes after they were written, so even with a population that fits into
  the caches a wave of `.security` document fetches is expected every 5 minutes (the first one about 5 minutes after
  `prime-api-key-caches`).
* Sanity check for the "caches fit" scenario: `security_crypto_tasks_per_authenticate` and
  `security_index_gets_per_authenticate` reported by `collect-security-stats-after` should be (close to) zero. In the
  "caches exceeded" scenario with uniform access they approach `1 - cache.max_keys / num_api_keys`.
* With Rally's `--test-mode`, `create-api-keys` and `prime-api-key-caches` run one iteration per client and
  `authenticate-api-key` runs for 10 seconds.
